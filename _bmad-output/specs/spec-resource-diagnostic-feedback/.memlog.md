---
topic: Resource-specific connection, account, and dataset diagnostic feedback
updated: 2026-09-23T00:06
---

- (direction) Build on the browser-safe error-contract foundation and focus this spec on successful responses containing degraded connection, account, inclusion, or dataset state.
- (capability) CAP-1: Account setup summarizes complete, partial, and failed discovery truthfully; success means mixed outcomes state what loaded, what did not, whether saved data remains, and when the check occurred.
- (capability) CAP-2: Each connection exposes a safe reason and recommended action; success means active-empty, unsupported-only, disabled, authorization-required, temporarily unavailable, syncing, and unknown states render distinct explanations and only valid actions.
- (capability) CAP-3: Each included-account dataset exposes durable diagnostic freshness and recovery facts; success means balances, positions, and activities show current, stale-usable, expired, syncing, or unavailable state even when they contain zero rows.
- (capability) CAP-4: Inclusion failures use their existing reason codes instead of generic copy; success means authorization-required, rate-limited, provider-unavailable, unusable-data, and stale-guard outcomes have distinct English and French explanations and appropriate recovery.
- (capability) CAP-5: Background synchronization preserves enough safe diagnostic history for the UI to explain degraded state; success means retry timing, last successful observation, and the current reason survive reload and scheduled worker execution where applicable.
- (capability) CAP-6: Resource feedback is accessible, localized, and regression-tested; success means summaries and changes are announced appropriately and contract, component, and browser tests cover the diagnostic matrix.
- (constraint) This spec depends on the browser-safe error-contract foundation for request-level failures but keeps HTTP 200 for valid partial or degraded resource snapshots.
- (constraint) Reason codes are bounded browser-safe categories and never include raw SnapTrade responses, provider error descriptions, credentials, unmasked financial information, or operator-only diagnostics.
- (constraint) Reconnect is offered only for authorization or connection-repair conditions; transient provider and network failures offer retry or a truthful wait state instead.
- (constraint) Existing saved selections and stale-usable portfolio evidence remain visible when policy currently permits them; messaging must distinguish retained data from fresh provider access.
- (constraint) OpenAPI is the public contract, and any durable diagnostic additions use reversible migrations and owner-scoped persistence.
- (constraint) English and French behavior must remain equivalent, including actions, timestamps, and accessibility semantics.
- (constraint) All code changes require cd backend && golangci-lint run in final verification under repository policy.
- (decision) InventoryConnection gains an optional diagnostic object with reason, recommendedAction, lastSuccessfulAt, and retryAt when relevant; absence means no additional diagnostic beyond the status.
- (decision) Connection reason codes include no_accounts_returned, no_supported_accounts, connection_disabled, authorization_required, provider_unavailable, sync_pending, and unknown.
- (decision) DatasetContext gains an optional diagnostic reason and recovery metadata; unavailable and expired datasets render even when their row arrays are empty.
- (decision) The account-setup summary is derived from returned connection and account facts and displays the inventory updatedAt timestamp; it never claims total failure when any connection result was returned.
- (decision) The user interface provides per-connection actions where the action can be scoped; a global action remains only for truly global retry or authorization conditions.
- (decision) Repeated unavailable states may show a bounded support reference only when supplied by the foundation contract; creating support tickets is out of scope.
- (decision) Non-goals: changing provider eligibility policy, adding providers, redesigning synchronization scheduling, exposing raw provider reasons, automatically repairing brokerage authorization, and redesigning the full Portfolio Showcase.
- (assumption) The provider adapter can distinguish zero returned accounts from returned-but-unsupported accounts; if implementation evidence disproves this, both initially map to no_accounts_returned without inventing a cause.
- (note) Primary audit sources are PortfolioPage.tsx, PortfolioShowcasePage.tsx, inventory.ts, i18n.tsx, backend inventory and sync models, the OpenAPI contract, and the supplied screenshot.
- (event) Self-validation pass 1 coherence: PASS; six capabilities each have testable intent and success, constraints preserve security and data semantics, non-goals bound scope, and the client-reported scenario anchors the success signal.
- (event) Self-validation pass 2 preservation: PASS; partial-result messaging, per-connection diagnostics, dataset visibility, inclusion reasons, persistence, localization, accessibility, future-safe fallbacks, and verification requirements are preserved in the kernel or failure-modes companion.
- (note) Wrapper-only content: conversational estimates and scheduling language were omitted because they do not change the build contract.
- (event) Spec finalized on 2026-09-23.
