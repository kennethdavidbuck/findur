topic: Browser-safe API error contract and enforceable frontend presentation
updated: 2026-09-23T00:06
---

- (direction) Deliver this foundation separately from resource diagnostics so it can establish reusable conventions and enforcement before domain-specific expansion.
- (capability) CAP-1: Failed HTTP requests expose a stable browser-safe structured error contract; success means every documented non-2xx application response validates against one envelope.
- (capability) CAP-2: The frontend classifies API, transport, timeout, and malformed-response failures without relying on exception text; success means each class reaches a deterministic UI failure code.
- (capability) CAP-3: The frontend owns localized error titles, explanations, and recovery labels through one exhaustive presentation catalog; success means every known code has English and French treatment and unknown codes use a safe fallback.
- (capability) CAP-4: User-visible failures provide truthful recovery and accessible announcements; success means actions match retryability and automated tests verify alert or status semantics, focus, preserved input, and action behavior.
- (capability) CAP-5: Repository controls make the contract the default for future changes; success means documentation, generated types, exhaustive compilation, and tests fail when a new error code lacks required handling.
- (constraint) OpenAPI at backend/api/openapi.yaml remains the source of truth; generated Go and TypeScript artifacts must be regenerated rather than hand-edited.
- (constraint) API responses carry bounded facts and codes, never localized prose, raw provider messages, stack traces, credentials, account identifiers beyond already authorized resource identifiers, or other sensitive diagnostics.
- (constraint) Frontend presentation copy remains localized in English and French and must not render server-supplied prose.
- (constraint) Degraded resources returned successfully are not represented as failed HTTP requests; their domain diagnostics belong to the resource-specific spec.
- (constraint) Existing authorization, session, inventory, inclusion, profile, preference, logout, and status behavior must remain owner-scoped and no-store where currently required.
- (constraint) Every code path must preserve an unknown-code fallback so independently deployed frontend and backend versions fail safely.
- (constraint) All code changes require cd backend && golangci-lint run in final verification under repository policy.
- (decision) The standard failed-request envelope requires code, retryable, and recommendedAction; retryAt and supportReference are optional bounded fields.
- (decision) Recommended actions are the closed set none, retry, reconnect, reload, and sign_in; the frontend may suppress an action when the current screen cannot perform it safely.
- (decision) Client-only failure codes cover network_unavailable, request_timeout, and malformed_response and use the same presentation layer without pretending they came from the API.
- (decision) The authorization-start form must be handled in-app so 400, 415, and 503 responses render recovery UI instead of navigating to raw JSON.
- (decision) Future-agent guidance will be added through the managed project-context workflow, and the pull-request template will require failure-mode and localization accounting.
- (decision) Non-goals: provider-specific raw diagnostics, changes to internal logging or alerting, resource-level reason persistence, a new customer-support workflow, and a full visual redesign.
- (assumption) No external support-ticket system exists, so supportReference is displayed only when the backend can safely supply an existing correlation value and is otherwise omitted.
- (note) Primary audit sources are backend/api/openapi.yaml and the current frontend request, page, localization, and test modules; the user supplied the desired contract direction in conversation.
- (decision) The failed-request envelope optionally carries bounded invalidFields so validation failures use the same closed response shape without losing field-level recovery.
- (decision) The recommended-action set includes review_input for validation and selection failures; retryable means safe to retry after the named recovery action, never automatic replay of unsafe requests.
- (event) Self-validation pass 1 coherence: PASS; five capabilities each have testable intent and success, constraints bend implementation, non-goals bound scope, and the success signal is demonstrable.
- (event) Self-validation pass 2 preservation: PASS; OpenAPI authority, frontend copy ownership, localization, accessibility, authorization raw-JSON recovery, exhaustive enforcement, future-agent guidance, and verification requirements are preserved in the kernel or failure-contract companion.
- (note) Wrapper-only content: conversational estimates and scheduling language were omitted because they do not change the build contract.
- (event) Spec finalized on 2026-09-23.
